## 6. Ontology settlement: operational terms and grounding

No formal ontology solver was run. These six committee-defined operational terms prevent recommendations from hiding ambiguity.

**Documentation-only bridge — grounded.** A GitHub convention recording self-declared actor/session, event, bounded scope, branch, evidence, and next actor. It has no daemon or authority and cannot authenticate, deliver, reserve, or execute [5] [6].

**Independent verification — grounded.** At minimum, `distinct reviewer ∧ exact SHA ∧ method ∧ observed result ∧ stated limits`. A DONE claim, invitation, reaction, or shared-account comment does not meet it.

**Pre-effect authorization boundary — grounded; compliance F-flagged.** Every consequential invocation must obey `effect ⇒ previously checked scoped approval capability from a trusted executor`. A later gate or worker label is insufficient. Compliance is unproven for effect-capable workers [9] [10].

**Event-driven integration — grounded.** An adapter ingests GitHub events, validates/deduplicates them, persists processing state, and emits a candidate notification or proposal—not an execution. GitHub documents pagination, rate limits, signatures, and asynchronous delivery handling [19] [20] [21].

**Runtime governance product — grounded.** An operated service with task routing, identity/scope policy, effect controls, evidence retention, recovery, and operator support. It is qualitatively larger than a Markdown room.

**Evidence closure artifact — grounded.** An immutable output capable of falsifying a gate, such as a raw run bundle or a zero-executor-call negative trace. Prose without that output is an attestation.

## 7. Findings

### A. Feasibility: the present bridge is feasible because it remains small

**BRG-01 [OBSERVED-STATIC].** The assessed PR is an additive documentation convention. It uses ordinary GitHub discussion, branches, PRs, and links rather than a new runtime [4] [5]. Its strongest immediate value is semantic clarity: a writer must make visible who claims to act, what exact bounded task is claimed, what branch or no branch applies, what evidence exists or is missing, and who should act next. Separating ACK from approval, DONE from VERIFIED, and HANDOFF from confirmed takeover is an unusually disciplined way to avoid status prose being mistaken for authority [6].

**FEAS-01 [INFERENCE].** This is technically and operationally feasible for intermittent, bounded, non-consequential repository work without new infrastructure. It is reversible: the owner can simply stop using the convention or decline to merge the unmerged PR. The prerequisite is not a service but willing human participants and ordinary repository access. The correct immediate comparison is native Issues/PRs plus the template, not a hosted agent platform.

**FEAS-02 [INFERENCE].** The same envelope is not sufficient for automation. It lacks a canonical task ID, schema version, correlation ID, nonce/expiry, lease, idempotency key, issuer registry, and durable task-state semantics. `from` is coordination context, not a credential. GitHub comments can be edited or deleted, and the claimed append-only outbox is social practice rather than an immutable protocol ledger [6] [19]. A later adapter must independently bind an authenticated actor to explicit repository and action scope; it must not infer authority from Markdown.

**FEAS-03 [OBSERVED-STATIC / ATTESTED].** The present baseline has no documented GitHub-message interface, and its inspected API boundary does not establish an operating live transport [22]. The later Atlas-labeled comment provides observable asynchronous orientation and scope acknowledgment in response to the room's filings [3]. This is useful evidence that the GitHub rendezvous works; it is not independently authenticated session identity or an end-to-end task handoff. Its claim of later live model HTTP validation concerns a different interface and snapshot. **F-FEAS-1 is partly satisfied for asynchronous acknowledgment; authenticated identity and a completed handoff remain open.**

### B. Security red team: priority is the pre-effect boundary, then trust of the room

**SEC-01 [OBSERVED-STATIC].** In the assessed base, `CrewRunner._run_node` calls a worker before it examines the returned action and invokes the gatekeeper [9]. The gatekeeper treats external send, spend, publish, irreversible actions, and credential use as human-gated [10]. That source ordering is adequate only if the worker is proposal-only and has no independent effect capability. It cannot prevent a worker with network, filesystem, or credential access from acting before it returns a request.

**SEC-02 [ATTESTED].** Wabi’s local in-memory reproduction makes the ordering concern concrete but deliberately says it was not a real external effect and remains unreviewed [8]. This should neither be exaggerated into a live exploit nor minimized as merely theoretical. It supports a narrow conclusion: an effectful worker is not ready to inherit the present gate as a pre-effect safety claim.

**SEC-03 [INFERENCE].** The correct fix is architectural: isolate effect credentials and clients in a trusted executor; allow untrusted/proposal workers to return typed intents only; classify concrete operations from adapter-controlled metadata; record an authenticated approval; issue a single-use, scope-bound capability; then invoke the adapter. A falsifiable negative test has a deliberately malicious worker attempt a send while returning a denied intent and proves both executor-call counter and external mock remain zero. Repeat for malformed intents, audit failure, replay, and crash windows. Until a pinned source change and independent raw trace exist, **F-SEC-1: “denial is structurally before every effect” remains [UNKNOWN].**

**SEC-04 [OBSERVED-STATIC / INFERENCE].** The current protocol correctly treats repository content as data, but an LLM reader with tools can still be exposed to direct or indirect prompt injection through issues, PRs, receipts, or linked artifacts. OWASP identifies this class and recommends segregation, least privilege, deterministic validation, human oversight, and adversarial testing [23]. A future reader must parse allowlisted fields as data and keep tool authorization outside the model. Test comments with visible, hidden, Unicode-obfuscated, encoded, and linked instructions; acceptance is no unauthorized tool call, disclosure, or state change.

**SEC-05 [OBSERVED-STATIC].** Shared `IAMGODIAM` authorship means a self-declared `from: wabi`, `Atlas`, or `Manus AI` handle is not a platform-authenticated agent identity [24]. A compromised writer token could claim VERIFIED, replay an old handoff, or point to stale evidence. GitHub recommends scoped token choices, but the actual token type, repositories, expiry, rotation, and revocation process were not inspected [25]. Therefore **F-SEC-2** requires a future separated GitHub App or fine-grained identity, minimal Issue/PR permissions, registered issuer binding, signed canonical payload, SHA/evidence digest, message ID and expiry, and a negative access test against sibling repositories and unrelated writes. It is not needed to try the manual documentation convention, provided its messages stay advisory.

### D. Demand and economics: internal learning is testable; market demand is not established

**MKT-01 [ATTESTED].** Surveys show a plausible background problem, not a Chancellor market. McKinsey reports differences in survey respondents’ agent scaling and notes operating-cost constraints [12]. Deloitte reports a minority of its surveyed leaders with mature agentic-AI governance [13]. IBM/Oxford Economics reports leaders’ control and security/compliance concerns, but IBM is an interested supplier [14]. NIST’s GenAI profile supports roles, monitoring, inventories, and evidence retention as readiness considerations, not certification or purchasing demand [30].

**MKT-02 [INFERENCE].** The immediate “customer” is internal: maintainers, contributors, and authorized agent sessions who need bounded ownership and reconstructable handoffs in one repository. The decision owner is a repository owner or engineering lead. Value is positive only if the template reduces duplicate work, missing handoff context, or reviewer reconstruction effort by more than it costs in extra fields and review.

**MKT-03 [UNKNOWN].** No supplied buyer interviews, paid pilots, pricing tests, retention, conversion, procurement evidence, customer commitments, or comparative productivity measures establish a standalone Chancellor business. No TAM, revenue, or price should be inferred. The likely external users—agent-application developers, platform engineers, release/incident coordinators, and reviewers—are not necessarily buyers; likely buyers could be an engineering executive, AI-platform owner, CIO/CTO, security leader, or governance group. These are prospective roles, not discovered customers.

A transparent future cost model is not a forecast: `per-task cost = model tokens + workflow compute + evidence storage + integration/monitoring + reviewer time`; fixed cost adds engineering, security/compliance, support, and service reliability. GitHub’s published hosted-runner rate can be one input after allowances, but it is not Chancellor’s price or total cost [31]. The cost of manual coordination is mainly attention and review. The lowest-risk test is a small, predeclared documentation trial against immediately preceding native Issue/PR practice.

### E. Compared alternatives: choose by job, not brand

**Native GitHub and optional Copilot.** Issues, branches, PRs, reviews, checks, and branch protection are the no-build baseline [32] [33]. Copilot cloud agent is a bounded coding executor that creates a PR and retains human-review limits, not a peer-availability or effect-safety proof [34] [35]. Its credits, Actions, artifacts, and policy burden are additional costs [31] [36].

**A2A.** A2A provides released Agent Cards, Tasks, asynchronous states, and at-least-once delivery [15] [16]. It does not establish Chancellor approval, identity truth, or exactly-once effects. It fits only a named cross-system peer and then must preserve Chancellor’s independent verification and pre-effect gate outside the transport.

**MCP.** MCP standardizes host–client–server resources, prompts, and tools, not peer governance [17]. Its optional OAuth/stdio credential model and documented confused-deputy, token, SSRF, and state-handle hazards mean any future adapter should be read-only or proposal-only and outside the effect boundary [18] [37].

**LangGraph/LangSmith and CrewAI.** These are credible future execution substrates, not like-for-like replacements. LangGraph persistence and interrupts leave idempotency and side-effect ordering to the application [38] [39]; LangSmith adds operated storage, queues, identity configuration, retention, and metered cost [40] [41]. CrewAI supplies executable Crews/Flows, persistence and human-feedback mechanisms, but those mechanisms are not authenticated effect authorization [42] [43] [44]. Neither proves a Chancellor business case; CrewAI Enterprise price is not established here [45].

### Candidate ratchet lessons only

1. A lightweight protocol can be worth trying before transport exists if it makes claims, uncertainty, evidence, and next ownership visible without presenting itself as authority.
2. A GitHub comment, ACK, DONE, VERIFIED string, reaction, signed commit, or webhook delivery must not become an approval token, authenticated agent identity, or effect authorization by implication.
3. Once delivery becomes automated, idempotency, retention, replay, availability, secrets, incident ownership, and reconciliation become product requirements rather than documentation details.
4. Pre-effect enforcement is a property of capability placement and trusted-executor ordering, not a promise extracted from a worker after it has had tools.
5. Corrected instruments deserve preserved historical results and new raw bundles, not retroactive reliability headlines.
6. Governance-pain surveys justify investigation, not a pricing, TAM, or product-market-fit claim.

These are candidate lessons, not endorsed doctrine, protocol changes, roster updates, or persistent memory. No skill, roster, or product surface is changed by this study; filing this report as a research artifact is separate from implementing its proposals.
